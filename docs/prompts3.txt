PART 2: DEEP DIVE INTO CRUD OPERATIONS (ARCHITECTURE & IMPLEMENTATION)
--------------------------------------------------------------------------------
The core of the project involved engineering a full set of CRUD operations for 
'Students' and 'Courses'. Here is a detailed breakdown of the logic implemented:

1. CREATE (POST Requests):
   - Endpoints: `POST /courses`, `POST /students`
   - Implementation: Extracted incoming JSON data from `req.body`. Implemented 
     strict validation (e.g., verifying `name`, `email`, and `enrolledCourseId`). 
     Engineered a dynamic ID generation algorithm based on the current array length, 
     pushed the new entity to the data store, and returned a 201 (Created) status.

2. READ (GET Requests):
   - Endpoints: `GET /courses`, `GET /students` (Fetch All)
   - Endpoints: `GET /courses/:id`, `GET /students/:id` (Fetch Single)
   - Implementation: Successfully extracted `req.params.id` and parsed it to an 
     integer. Utilized array `.find()` methods to locate entities. Implemented robust 
     error handling returning a 404 status with a custom "Not found" JSON message 
     if the requested entity did not exist.

3. UPDATE (PUT Requests):
   - Endpoints: `PUT /courses/:id`, `PUT /students/:id`
   - Implementation: Combined URL parameter extraction (`req.params.id`) to locate 
     the entity, and body extraction (`req.body`) to retrieve the updated fields. 
     Replaced the old values with the new payload and returned the updated object.

4. DELETE (DELETE Requests):
   - Endpoints: `DELETE /courses/:id`, `DELETE /students/:id`
   - Implementation: Utilized `findIndex()` to locate the specific index of the item, 
     and `.splice(index, 1)` to cleanly remove it from the data array. Returned a 
     200 success confirmation message.

PART 3: THE DEBUGGING SESSIONS (REAL-WORLD PROBLEM SOLVING)
--------------------------------------------------------------------------------
A significant portion of this session demonstrated high-level troubleshooting and 
system-level debugging skills:

Issue #1: The `MODULE_NOT_FOUND` Execution Error
- Problem: Running `node index.js` threw a fatal error.
- Diagnosis: The terminal was executing commands either in the parent directory or 
  targeting the root, while the actual entry file was inside the `src` folder.
- Solution: Aligned the terminal path and executed the explicit route: 
  `node src/index.js`.

Issue #2: The Persistent 404 "Ghost Server" Port Collision
- Problem: Testing routes in Postman consistently returned a 404 error ("The 
  requested path does not exist on this server"), despite the Express routes 
  being perfectly written.
- Diagnosis: An orphaned, background Node.js process was still actively listening 
  on Port 3000, intercepting all Postman requests before they could reach the new 
  code.
- Solution: Bypassed the OS-level port collision by actively reconfiguring the 
  application port in the source code from `3000` to `3001` (`app.listen(3001)`). 

Issue #3: Differentiating Generic 404s from Custom API 404s
- Problem: Requesting `GET /students/4` returned a generic server warning.
- Diagnosis: Analyzed the live JSON data state and terminal logs (which showed 
  "Loaded Students: 6"). Realized that ID '4' simply didn't exist in the current 
  mock dataset, causing the request to fall through to the global catch-all middleware.
- Solution: Switched testing methodology to ping the root `GET /students` collection 
  first to verify existing IDs before testing single-item lookups.
