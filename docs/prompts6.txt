### Instruction 18 · 2026-11-04
**Topic:** The instructor requests the use of `.then()` within the middleware components.
**Instruction:** "I want to do this because my instructor asked me to use `.then()`."
**Response:** All six middleware components now use the following structure: `Promise.resolve().then(validate).then(fetch).then(set req + next).catch(next)`. The `Promise.resolve()` initiates the chain, ensuring that any **synchronous** error thrown is caught by the `.catch` block; within that block, `err.status` is used solely to determine the appropriate log line.
**Result:** Six middleware functions have been converted to this structure.

## Step 7 — Error Handling and Review

### Instruction 19 · 2026-11-04
**Topic:** Errors related to `fs.promises`.
**Instruction:** "What kind of errors might occur when using `fs.promises`?"
**Response:** 1) Corrupted JSON file → `DATA_FILE_CORRUPTED` → `500` error. 2) `ENOENT` error (file not found) → creation of an empty array `[]` (via `fs.mkdir({ recursive: true })`); Weak point: A failure during `mkdir` or when writing to a file might also manifest as `ENOENT`. 3) `EPERM` (permission denied) or `EBUSY` (resource busy) errors during a file rename operation indicate a temporary lock; in such cases, a retry is attempted, accompanied by a "hint" regarding the lock.
**Outcome:** Mapping was performed, followed by the implementation of two improvements.

**Guideline 20 · 2026-11-04**
**Topic:** How can the code be improved?
**Guideline:** "How can the code be improved?"
**Response:** In the event of an `EPERM` error on a read-only file, the code performs 5 retries before returning a `500` error—essentially treating a permanent error as a transient one. Furthermore, the absence of the `SECRET_KEY` environment variable allows the server to start up in a broken state. Additionally, the log for the `500` error lacks both the `err.code` and the file path. Fixes: Enhanced logging for `500` errors; inclusion of a "hint" regarding locks; and the implementation of pre-flight checks prior to starting the server (`listen`).
**Outcome:** All three fixes have been implemented and verified (including checks for read-only permissions and exiting with an error code of 1 upon failure). ### Directive 21 · 04-11-2026

### Directive 24 · 05-11-2026
**Subject:** Addressing significant issues raised during the review.
**Directive:** "Fix the significant issues and detail what has been corrected."
**Response:** 1) **Data modification without isolation (copying)** — The `update` operation previously passed the array retrieved from `readAll` both to the mutator function and to `res.json`; `structuredClone` is now used, ensuring that only a copy is written to the file. 2) **Deadlock risk** — The `removeEnrollmentsFor` function deleted the parent entity while holding a lock on the enrollments; this has been resolved—the deletion now occurs in the correct order: the parent entity first, followed by the enrollments, with a clear notification provided should the second step fail. 3) **Naming** — Renamed a local variable to `enrolledStudents` (the response key remains `enrollmentedStudents`); fixed spacing in `courseRoutes.js`. **Result:** 12 isolated tests + a live HTTP smoke test passed successfully; the actual data (`sha256`) remained unchanged; `docs/CHANGES.md`, section 7.3.

## Step 9 — Chaining Style

### Directive 27 · 05-11-2026
**Subject:** `jsonStore.js`, the three services, `index.js` — and this file.
**Directive:** "Adjust all services, the internal mechanisms of `jsonStore`, and the initialization test to a consistent style: using `().then` chains, without `async`/`await`."
**Response:** Four of the five specified files have been updated (the fifth, `enrollmentService.js`, does not exist—its correct name is `enrollmentsService.js`). In `jsonStore`, the last remaining `async/await` was removed; the initialization test reads the three files using `reduce` over `().then` chains, with a single `().catch` block that triggers an exit. During the process, three issues were discovered, all of which have been fixed: 1) **Declaration Order** — the `writeAll` function was called before being declared (a state known as the TDZ, or Temporal Dead Zone), causing a `ReferenceError` that resulted in a broken chain; it is now declared at the beginning of the code.2) **deadlock** — creating a missing file through the store's own queue waits on itself; creation moved to its own `createChain` guarded by `fs.access`. 3) **double read** — `fs.readFile(...).then(ok, recover)` could hand the inner result to the parse step; existence checked first, then exactly one `readFile`. Unchanged: names, response shapes, id bases, atomic writes.
**Outcome:** All five in chain style; `CHANGES.md` §9; isolated tests passed; real data verified by `sha256`.
